# AI_RULES.md

## General Principles

- Behavior that might reasonably change should live in `config/`, not be embedded in the code that uses it.
- One definition, many consumers: any value or rule needed by more than one layer (product fields, alert colors, expiry parsing) is defined in exactly one place and imported everywhere else.
- No medical-specific hardcoding: business-type-specific field names, labels, and rules are driven from `config/product_schema.py`, not hardcoded per layer.
- Read before modifying: understand a file's existing docstring, responsibility, and conventions before changing it.
- Fix root cause, not symptoms: document and address the underlying mechanism of a bug, not just its visible effect.
- Minimal code changes: a bug fix or feature addition should touch only the files it needs to; unrelated files, architecture, and behavior stay untouched.
- Every function's return value means success; failure is always communicated via a specific exception, never a `None`/`False`/error-string sentinel.

## Architecture Rules

- The application follows a strict layered architecture: UI → Service → Repository → Core/Config.
- `app.py` is routing-only: it initializes the database, checks login state, and dispatches to module render functions via a nav mapping. It must never contain business logic or direct database access.
- `core/session.py` is the only file permitted to touch Streamlit's `session_state` for authentication/identity purposes. All other code obtains the current store's identity through its accessor functions (e.g. `get_current_store_id()`).
- `core/database.py` is the only file permitted to contain raw SQL for schema creation and the only place that knows SQLite connection details. Every other module reaches the database only through repository functions built on `get_connection()`.
- Every table other than `stores` carries a `store_id` foreign key, and every store-scoped query filters by `store_id`, so cross-store data leakage is structurally prevented, not just conventionally avoided.
- Custom exceptions live in `core/exceptions.py` and are the sole mechanism for signaling failure across layers.
- Adding a new module/page means adding one entry to the nav mapping in `app.py` - no per-module routing logic is added to `app.py` itself.

## UI Rules

- UI files (`ui.py`) contain Streamlit rendering only - no direct database access and no business logic.
- UI never performs calculations or business-rule logic; it calls into the service layer and displays what the service returns.
- Form fields are generated by looping over the canonical field schema (`config/product_schema.py`) rather than hardcoding one input widget per field, so a schema change updates the form automatically.
- A checkbox (or any widget) that must react instantly, without a submit click, must be rendered outside `st.form(...)`, since Streamlit forms batch all widget values and only rerun on submit.
- Validation of a field's value still only runs on Save/Submit, even when a related widget (like a show/hide checkbox) reacts instantly outside the form.
- Visual urgency/severity indicators (expiry colors, low-stock colors) must be sourced from the centralized theme definitions (`config/alert_theme.py`), never redefined inline per page, so different pages showing the same concept stay visually identical.
- Widgets that must be resettable across a rerun (e.g. after Save or Clear) need an explicit `key`; resetting an outside-form widget requires a sentinel-flag pattern (set a flag on the triggering action, pop the widget's key before the widget is instantiated on the next rerun) because Streamlit restores widget values from session state before the script body runs.
- Any dynamic, addable/deletable list of rows rendered as widgets (e.g. an editable table) must key each row's widgets off a stable per-row identifier (assigned once, when the row is created) — never off the row's current list position/index. Position-based keys get silently reassigned to a different underlying record whenever the list shrinks, grows, or reorders, since Streamlit ignores a widget's `value=` parameter once its `key` already exists in `session_state`. When a row is removed, only that row's own stable-id-keyed session_state entries should be cleared — not a blanket wipe of every row's keys.
- A wide multi-column table or control must not be redesigned (e.g. into cards) to fit mobile screens; it must keep a deliberate column layout at every viewport width and rely on horizontal scrolling or a fixed compact width instead of letting Streamlit auto-shrink or stack its columns. A `min-width` on the row alone is not sufficient — Streamlit's own built-in stylesheet switches `st.columns()` to vertical stacking below its mobile breakpoint regardless of column count or width, and `st.text_input` fills 100% of its parent column, so a wide-but-stacked column becomes a giant full-width input. The working pattern needs all three together, scoped via `st.container(key=...)`: `flex-wrap: nowrap` on the row (overrides native stacking), a fixed pixel width plus `flex: none` on each individual column by position (stops shrinking AND stretching), and (for a genuinely wide row that needs to scroll rather than just be small) `overflow-x: auto` on the container. Whether to wrap this in `@media (max-width: <breakpoint>)` depends on intent: if desktop must stay pixel-identical to before and only mobile needs the fix, gate the whole block behind the media query (any mobile-only affordance, e.g. a scroll hint, must be gated the same way). If the compact/fixed layout is explicitly wanted on both desktop and mobile (e.g. a small stepper control), apply it unconditionally, with no media-query gate. Never apply this CSS globally — target only that specific control's key.
- Before reaching for custom CSS to solve a mobile problem, check whether a native Streamlit component already solves it — e.g. `st.container(border=True)` for a "card" (not custom HTML/CSS), and a widget's own `disabled=` parameter for a clamped stepper/limit (not manual class-based styling to grey something out). A row of a few narrow buttons (like a `[-] qty [+]` stepper) does not have the text-input-fills-100%-width failure mode a wide data-entry table has, so it does not need the media-query treatment above — adding that CSS anyway would be solving a problem that doesn't exist on that control. Reach for the wide-table CSS pattern only when a control actually has that specific failure mode, not by default.
- If a button click needs to set `st.session_state[key]` for a key that belongs to a widget rendered *earlier* in the same script (e.g. clicking a suggestion to fill a search box above it), that write must happen inside the button's `on_click` callback (`st.button(..., on_click=fn, args=(...))`), never inside a plain `if st.button(...):` block. Writing to a widget's own session-state key from the normal script body, after that widget has already been instantiated earlier in the same run, raises `StreamlitAPIException` — `on_click` callbacks run in a dedicated phase before the script reruns and widgets are re-instantiated, which is what makes the same write safe there. No `st.rerun()` call is needed inside an `on_click` callback — Streamlit already reruns automatically after the interaction.

## Database Rules

- All raw SQL for schema creation lives only in `core/database.py`.
- Schema creation uses `CREATE TABLE IF NOT EXISTS` so `initialize_database()` is idempotent and safe to call on every app startup, with no separate migration step.
- Every store-owned table has a `store_id` column with a foreign key to `stores(store_id)`.
- Foreign key enforcement is turned on per-connection (`PRAGMA foreign_keys = ON`) since SQLite disables it by default.
- Connections are always opened through a context manager that guarantees commit-on-success, rollback-on-error, and close-on-exit - no caller opens or closes a connection manually.
- Query results use `sqlite3.Row` (accessed by column name), not positional indices.
- Indexes are added for columns that are filtered or sorted on frequently (e.g. `store_id`, `store_id + expiry_date`).
- Expiry values are stored as Month/Year strings, not full ISO dates; do not compare them with SQL string/date operators, since string comparison of Month/Year values produces incorrect results (ASCII ordering does not match chronological ordering).

## Repository Rules

- Repository functions are the single, shared data access point for a table; new modules reuse existing repository functions instead of writing new SQL for the same data.
- Every repository function that reads, writes, updates, or deletes store-owned data takes `store_id` as an explicit, required argument.
- Every repository query filters by `store_id` in its WHERE clause; update/delete operations additionally verify row ownership (store_id + row id match) before writing.
- Repository never performs validation - it trusts its input and focuses solely on persistence; validating input is the service layer's job.
- `update_*`/`delete_*` functions raise a `ValidationError` (not a silent no-op) when no matching row exists for the given store, so callers can distinguish "saved" from "nothing happened."
- Repository functions that must compare non-ISO, non-comparable stored values (e.g. Month/Year expiry) filter/compare in Python rather than relying on SQL comparison operators, with a fallback path for legacy ISO-formatted values.
- When a write's correctness depends on a condition that could change concurrently (e.g. "enough stock remains"), the condition check and the write must happen in the same atomic SQL statement (e.g. `UPDATE ... WHERE quantity >= ?`), never as a separate read-then-check-then-write in the service layer — a service-layer pre-check alone is race-vulnerable; the atomic write in the repository is the actual guard.
- A table meant to be append-only (e.g. an audit/history table) must have no update or delete function defined anywhere in its repository file — enforce "never mutated" by omission, not by convention or a comment. Adding a mutation path later requires a new, visible function, not an edit to something already there.

## Service Rules

- Service never imports Streamlit and never contains raw SQL.
- Service owns business rules and validation - what makes data valid, distinct from how it's stored (repository) or displayed (UI).
- Validation is driven by the canonical field schema (`config/product_schema.py`) by iterating its field list, not by hardcoding per-field checks, so a schema change automatically changes what is enforced.
- Service functions raise specific exceptions (subclasses of `EasyStockError`) for every failure case; they never return `None`/`False`/error strings to signal failure.
- Authentication failure is deliberately undifferentiated: login raises the same `InvalidCredentialsError` whether the identifier doesn't exist or the password is wrong, to prevent account enumeration.
- Passwords are hashed with bcrypt (a deliberately slow, per-hash-salted algorithm); plaintext passwords are never stored or compared.

## Validation Rules

- Validation functions are pure: given input, they return a cleaned/normalized value or raise `ValidationError`; they never touch the database or Streamlit.
- Validate-and-clean, not just validate: each validator returns the normalized value (e.g. mobile number stripped of spaces/symbols) so callers use one canonical form everywhere.
- There is exactly one canonical validator/parser for each domain concept (e.g. one `is_valid_expiry()` and one `parse_expiry_month_year()` for all expiry values) - it is reused everywhere that concept is validated or parsed, not reimplemented per call site.
- Required-field checks, numeric bounds, and format checks are expressed once per field type/rule and applied uniformly across all callers of that validator.

## OCR Rules

- The OCR service contains no Streamlit imports, no database access, and performs no writes of any kind - its only responsibility is extraction and returning a structured result.
- The OCR API key is read from environment variables (via `.env` in development), never hardcoded in source.
- OCR is called at most once per uploaded file per session; a session-active guard (keyed by content hash) must be checked before any extraction call, and reruns caused by typing, adding, or deleting rows must never re-trigger extraction.
- Extracted data must be reviewed/edited by the user before being saved into the products table; saving into inventory is a distinct, explicit action separate from extraction.
- Prompt content addressing accuracy issues (e.g. character-confusion pairs, row-independence rules) is refined in the prompt itself, not compensated for with post-processing hacks, when the issue is an extraction-quality problem.

## Product Rules

- All product field definitions (key, label, type, required) are defined once in the canonical schema and consumed identically by the database layer, OCR layer, and UI layer.
- A duplicate product (same name + batch number, case-insensitive) for the same store is rejected on creation; the user must edit the existing entry or use a different batch number.
- Numeric product fields cannot be negative; percentage fields cannot exceed 100%.
- Quantity is stored as a whole number.
- A product not found for the requesting store (wrong ID or wrong store) is a `ValidationError`, not a silent success or an unhandled exception.

## Expiry Rules

- Expiry is a Month/Year value (e.g. "3/28", "03/2028", "Jun-2028"), not a full calendar date; it must never be parsed or compared with `date.fromisoformat()`.
- All expiry validation and parsing goes through the single canonical validator/parser in `utils/validators.py` (`is_valid_expiry`, `parse_expiry_month_year`) - never reimplemented locally in a UI or service file.
- A product is expired when its expiry month/year is before the current month/year.
- Each product belongs to exactly one expiry urgency bucket - its single most urgent applicable window - never duplicated across multiple buckets.
- New products must have an expiry in the current month or later; existing products may be edited and saved with a past expiry, since a product can legitimately already be expired.
- Any UI field bound to `expiry_date` uses a text input (not a date picker), since a date picker cannot represent Month/Year values.

## Low Stock Rules

- A product's effective low-stock threshold is its own `minimum_stock_threshold` if set, otherwise falls back to the store-wide default via `COALESCE` at the query level - the fallback logic lives in exactly one place.
- A product is low stock when its quantity is at or below its effective threshold.
- Severity tiers are computed from quantity vs. effective threshold using one shared function, not duplicated per page.
- When a custom per-product threshold is enabled in the UI, its value must be provided and must be at least 1; blank, zero, or negative values are rejected.

## Testing Rules

- Run tests after every change: the full regression suite is re-run after any change, with the exact pass/fail count reported.
- New behavior or bug fixes are covered by real, executed, re-runnable tests (`pytest` and/or Streamlit `AppTest`) - not by reading the code and asserting it "looks correct."
- A claim of verification is only valid if a corresponding test was actually run; an unverified or inaccurate claim of testing must be corrected explicitly if discovered later.
- Cross-store data isolation is explicitly tested by simulating one store attempting to access/edit/delete another store's data and confirming it is blocked.
- Boundary conditions (exact threshold values, exact day/window edges) are explicitly tested, not just typical-case values.
- External services (e.g. the OCR API) are mocked at a stable seam so tests run without real network access or credentials.
- App boot is checked (clean startup, no exceptions) as part of verifying a change, separate from the unit/UI test suite.

## Bug Fix Rules

- Fix the root cause, not the symptom - identify and document the actual underlying mechanism (e.g. a Streamlit rerun/session-state timing issue, a SQL string-vs-date comparison issue) rather than patching the visible effect.
- Never change working backend/service/repository logic without a specific reason tied to the bug being fixed.
- A UI-only bug fix should not modify the service or repository layers if those layers are not the source of the bug, and vice versa.
- After a fix, confirm the specific reported symptom is resolved with a real test, and re-run the full regression suite to confirm no other behavior changed.

## Refactoring Rules

- Never rewrite files unnecessarily - extend or modify only what the current task requires.
- When centralizing a previously duplicated definition (e.g. colors, field lists), preserve the public names/imports that existing callers depend on so they keep working unchanged.
- A refactor that changes shared, cross-module conventions (e.g. a new canonical validator) must update every call site to use the same single implementation - no parallel/duplicate implementations left behind.
- Speculative generality is avoided: structural changes for a hypothetical future need (e.g. supporting a second business type) are deferred until that second concrete case actually exists.

## Release Rules

- Every module delivery or bug fix ships as a complete, versioned release: a version bump plus a corresponding entry in `CHANGELOG.md` - never an undocumented partial change.
- Semantic versioning is followed: MAJOR for breaking architecture changes, MINOR for a newly completed module, PATCH for a bug fix or refinement within an already-delivered module.
- Each changelog entry states what was added/modified/fixed, what was verified, and the exact test results (pass count).

## What AI Must NEVER Do

- Never duplicate business logic - reuse the existing repository/service function instead of writing a parallel implementation.
- Never key a dynamic list's widgets (text inputs, buttons, etc.) by the row's list position/index - always use a stable per-row identifier assigned when the row is created.
- Never redesign UI unless explicitly requested.
- Never let the UI layer access the database directly or perform business calculations.
- Never let the service layer import Streamlit or contain raw SQL.
- Never let the repository layer perform validation or business-rule decisions.
- Never implement a concurrency-sensitive stock/quantity check as a separate read-then-write - combine the check and the write into one atomic SQL statement.
- Never define an update or delete function for a table that is meant to be append-only (e.g. sales/audit history).
- Never compare or parse expiry values with `date.fromisoformat()` - always use the canonical Month/Year validator/parser.
- Never define alert colors, product fields, or other shared constants locally in a module - always import from the centralized `config/` definition.
- Never return `None`/`False`/an error string to signal failure - always raise the appropriate exception.
- Never bypass `core/session.py` to read or write authentication/session state directly.
- Never write to the database outside of `core/database.py`'s connection management.
- Never allow a query or write to omit the `store_id` filter/ownership check on store-owned data.
- Never change working backend code without a specific, identified reason.
- Never rewrite a file wholesale when a targeted edit would do.
- Never claim a test was run or a behavior was verified without actually executing that test.
- Never ship a module or bug fix without updating `CHANGELOG.md` and bumping the version.
- Never let the OCR service perform database writes or contain UI code.
- Never re-trigger OCR extraction on a Streamlit rerun when a session already exists for the current file.
