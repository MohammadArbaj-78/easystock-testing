- **Phase 9.1**: fixed the preprocessing defect. Root cause: `geometry._find_largest_quadrilateral()` accepted any 4-point contour with `area >= 1` as the document boundary, with no check relative to the image's actual size. On the real failing invoice photo (`IMG20260616160324.jpg`, 3072x4096), the accepted candidate measured 65,746 px^2 against a 12,582,912 px^2 frame - 0.52% of the image - and the resulting perspective warp destroyed the image to an unusable 86x786 sliver. Fix: `_MIN_QUADRILATERAL_AREA_RATIO = 0.20` added as a guard immediately after the existing near-zero-area check; a candidate below this ratio is rejected and the pipeline falls through to its existing, already-frozen fallback (original image preserved unchanged). Verified: the failing image now stays 3072x4096; the previously-successful second real image (`IMG20260728170635.jpg`) is unaffected; a legitimate large synthetic quadrilateral (70.4% of frame) is still detected and correctly warped end-to-end. New file `tests/test_preprocess_geometry_regression.py` added specifically for this fix (5/5 passing). The project owner supplied a "previous stable version" of the preprocessing files for comparison; it was found byte-for-byte identical to the then-current files, so this fix is based on direct root-cause tracing against the real failing image, not on restoring old behavior.

## Regression Risks

- `field_evidence.py`'s numeric-conflict signal (`mrp`/`quantity` only) is a deliberately conservative, page-level heuristic (no row-detection/cropping exists to correlate OCR text to a specific field) - documented in-code as approximate, not a claim of row-level correlation. A future phase adding real per-row OCR correlation would need to revisit this.
- `field_evidence.py`'s `_VALIDATION_FLAG_MAP` only maps validation.py's 8 existing flags onto the 5 fields it covers - `name` and `quantity` have no mapped flags today (validation.py has no rule for either), so those two fields' `validation_result` is always "PASS" under current rules. Not a bug - an honest reflection of validation.py's actual current coverage.
- The Phase 9.1 preprocessing guard (`_MIN_QUADRILATERAL_AREA_RATIO = 0.20`) is a fixed threshold chosen from one proven-bad case (0.52%) and one synthetic legitimate case (70.4%) - if a future real invoice legitimately has a very small in-frame document (e.g. a small receipt photographed with lots of background), this guard could reject a genuinely valid quadrilateral and fall back to the un-warped original image. This is a conservative trade-off, not a defect - flagged here for awareness.
- `tests/test_review_service.py`'s `TestPageIsolation`/`TestValidateMedicine` tests were corrected in Phase 9 to assert current, documented, intended behavior after being proven stale (not weakened) - a future session should not assume these need further changes without new evidence.
- Phase 12's `return_medicine()` requires every `PRODUCT_FIELDS` value to already be present and valid on the existing record (it re-runs `edit_product()`'s full validation), since it reuses that path rather than a narrower quantity-only update. If a legacy record somehow has an invalid value in an unrelated field (e.g. a corrupted expiry), `return_medicine()` would raise `ValidationError` rather than silently succeeding - this is intentional (no silent partial writes) but worth knowing if a future report describes Return Medicine "failing" on an old record.
- Phase 12's three search-bar widget keys (`products_search_term`, `expiry_alerts_search_term`, `low_stock_search_term`) must remain unique if any of these three UI files are edited again - the original bug was caused by omitting `key=` entirely, not by a wrong value, so the failure mode to watch for in future edits is the same omission recurring on a new/copied widget.
